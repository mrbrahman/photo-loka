# Queue Gates, Events, and Live Status - Design

## Why

Two problems with one shared root. First, the admin Indexer page (web/js/components/pl-admin-indexer.js) polls getIndexerStatus every 1.5s; left open while idle it logs requests forever. We want live updates that go silent when nothing is happening. Second, gating grew ad-hoc: the queue has two bespoke gating-only hooks (CanDispatch, OnDrained), and geo rate limiting regressed - the old Node.js server held rate-limited items in the queue and auto-resumed at the hour/day rollover, but the Go migration turned it into a mark-and-skip (RATE_LIMITED status, item consumed, no retry). The root of both: the queue needs a general notion of "reasons I am not dispatching" plus a general "something changed" event stream. Once those exist, resource gating, rate limiting, and live UI all fall out of the same two seams.
## Current state (orientation)

internal/queue/queue.go - the Queue: a priority task queue with Pause/Resume, SetConcurrency, GetStatus (Pending/Active/Completed/Failed/IsPaused/MaxConcurrency), Enqueue, Kick, and gating hooks to be removed: SetCanDispatch(func() bool) (pre-dispatch predicate; false leaves tasks pending) and SetOnDrained(func()) (fires on busy->drained, used to kick gated dependents).
internal/pipeline/pipeline.go - the orchestrator. Creates one queue per stage (realQueueFactory -> queue.New), wires gates in wireGates (sets CanDispatch = !upstreamBusy on gated stages, OnDrained = kick dependents on upstreams), and merges queue counters with the pipeline-derived gatedClosed in StageStatus. internal/pipeline/stage.go has Stage{Name, Fn, Queue, Downstreams, GatedBy, Enabled} and upstreamBusy().
internal/geo/ - finalizer.go (FinalizeGeo: derive GPS -> non-US exiftool resolve, or US DB exact match -> DB proximity match -> geonames API on miss), ratelimiter.go (rateCheck/rateIncrement over hourly/daily counters, persisted).
internal/frames/ - a working SSE implementation to copy for mechanics only (its route is public/no-auth): RegisterSSEClient/notifySSE, the /frame/events handler, and EventSource in web/js/frame.mjs.
Verified ownership fact: queues are created by the pipeline package, not indexing. indexing only holds hook function-vars that pipeline.Init populates. Think "indexer pipeline" as one unit, but all queue construction, gate registration, and event wiring live on the pipeline side.
## Core model - three layers, each owning only what it can compute
**1. The queue owns execution and its own event stream.** Its only built-in features are pause (on/off) and concurrency (max parallel). It also holds a set of named gates (`{name, isOpen func() bool}`) registered by their owners; the queue does not know what any gate means. Dispatch requires `!paused && slot-available && every gate open`, evaluated as a short-circuit AND at dispatch time. The first gate that returns false is the block reason: there is exactly one evaluation and one truth, and that same result is what the UI shows. We do NOT separately evaluate all gates to build a "full closed set" for display. The queue emits an event on every dispatch-cycle transition (enqueue, start, completion, pause, resume, concurrency change, gate-block/clear seen during a dispatch attempt) carrying its own facts: counters, paused, concurrency, and the current block reason (a gate name or none). `Kick()` forces a re-evaluation; gate owners call it when their condition may have changed.

Key insight (resolves a subtle trap): the queue pulls gate state at evaluation time; it does not watch gate conditions. A gate can open (an upstream drains) without the gated queue knowing -- it only learns by re-evaluating on the next dispatch attempt. That means the queue cannot spontaneously emit "gate opened" while idle, and that is fine: gate/block state is only meaningful when there is work to dispatch. An empty queue is just "idle"; whether a gate is notionally closed is invisible and irrelevant. When work arrives, counters change, a dispatch cycle runs, the first closed gate becomes the block reason, and the queue emits "blocked by X". When the gate owner later kicks it, it re-evaluates and either dispatches or emits the next block reason. Because every UI-relevant transition happens inside the queue's own dispatch cycle, the queue is the complete owner of the UI event stream: it reports counters and the block-reason gate name directly, without the pipeline telling it whether it is gated.

**2. Gate owners register gates and kick.** A gate lives with the layer that owns its condition; the queue is a neutral host. Resource gating (owner: pipeline): for each gated stage, register a gate named "resource" with `isOpen = !stage.upstreamBusy()`, and kick the gated queue when an upstream reaches busy->drained. Rate limiting (owner: geo): register a gate named "rate" on the geo API queue with `isOpen = rateCheck()`, and kick it on the hour/day rollover (a timer) to auto-resume. Adding a future gate type = register another named gate + kick it when its condition changes; no queue changes needed.

**3. Orchestrator and SSE are both subscribers to the event stream.** The pipeline subscribes to each stage queue's events and, on seeing an upstream reach drained, kicks the stages gated behind it: this replaces the bespoke OnDrained callback with "watch the general event stream." The SSE broadcaster subscribes to the same events and forwards per-stage status to browsers; the Indexer page swaps its poll for an EventSource (silent when idle, live under load). The queue event carries queue-level facts plus the block-reason gate name; two UI fields are pipeline-level, not queue-level: `enabled` (the `Stage.Enabled` master switch) and any friendly label. So the SSE payload is a per-stage snapshot: queue event fields + the pipeline's static enabled/identity overlay. The block reason comes straight from the queue; the pipeline no longer computes `gatedClosed` for the UI.

## Resulting queue surface

`Enqueue`/`EnqueueMany`, `Pause`/`Resume`, `SetConcurrency`, `GetStatus` (now including the block reason), `RegisterGate(name, isOpen)` plus a way to clear/replace gates (for live re-wire on config Apply), `Kick`, and a subscribe mechanism for the event stream (`Subscribe() <-chan Event` or `OnChange(func(Event))` -- to decide). Deleted: `SetCanDispatch` (becomes the gate set) and `SetOnDrained` (becomes the orchestrator watching the stream).

## Invariants carried over (from pipeline-dag-design.md)

Gate is evaluated at dispatch time, not enqueue time (closes the race where the condition changes the instant a task starts). "Busy" = running OR pending; a resource gate opens only when all gating upstreams are fully drained (both zero). The re-check fires on the busy->drained transition, not on every completion (in the new model, the orchestrator reacting to the drained event). Gating never touches the paused flag; pause is reserved for explicit admin control, and paused && allGatesOpen are independent.

## Geo redesign (ponder this part most)

**What the code does today.** FinalizeGeo resolves geo for one item: derive GPS (none -> done); non-US -> resolve from exiftool geolocation already in geo_lookups (no API); US -> DB exact match, then DB proximity match (no API on a hit); only on a cache miss -> geonames `findNearestAddress`, then possibly a second `postalCodeLookup` if placename is empty (both count against the rate limit). Rate limiting today: `lookupGeonames` calls `rateCheck()`; if over budget it sets RATE_LIMITED and returns -- item consumed, not retried. That is the regression. Node.js reference: a single geo queue with `pauseConditionFn = checkGeonamesRateLimit` (a whole-queue pre-dispatch gate) plus a `setTimeout` resetting counters at the hour/day boundary (+30s). Node held ALL geo work -- including cache-resolvable items -- behind the gate. There were NOT two queues (a recollection of two does not match the code on disk).

**The key optimization: cache-seeding funnel.** The proximity cache means one API call seeds the cache for all nearby items. 200 photos at the same place: the first cache-misses and calls the API, writing a geo_lookups row; the other 199, if they check the cache after that row exists, hit the proximity match and make zero API calls. So whether you spend 1 API call or 200 depends entirely on ordering. Two consequences: the cache check must be re-evaluated as late as possible -- immediately before the API call, not once up front (else the cache is cold for all of them); and the API path must be serialized at concurrency 1 so each item's late re-check sees the rows written by items ahead of it. Concurrency 1 serves BOTH the rate limit and cache coherence; raising it re-introduces the API stampede. Gating the whole geo queue (as Node did) needlessly stalls cache-resolvable items when the budget runs out; since a personal collection has many photos at the same places, cache hits are common, so we gate only the API path.

**Structure: two internal queues within one stage.** The pipeline still sees a single geo-lookup stage. Internally:

(1) A geo-lookup queue (ungated, concurrency may be > 1) does GPS derivation, non-US resolution, and the FIRST exact+proximity cache attempt: a cache hit / non-US / no-GPS resolves and is done; a US cache miss hands the item to the API queue.

(2) A geo-api queue (rate-gated, concurrency 1): its per-item task RE-CHECKS the cache first (a sibling moments ago may have seeded it) -- if now a hit, resolve without an API call; if still a miss, call geonames (this one call seeds the cache for everyone behind it), write the geo_lookups row, resolve fields. The "rate" gate is registered on this queue only (`isOpen = rateCheck()`); when closed, items wait here (held, not marked-and-skipped), and a rollover timer kicks the queue to auto-resume. `rateIncrement()` stays inside the task after a successful call; the RATE_LIMITED mark-and-skip is removed.

Invariant: with concurrency 1, item N+1 does not dispatch until N returns, and N writes its geo_lookups row before returning, so N+1's re-check reliably sees it -- the write must stay inside the task and before return.

**Geo open decisions.** (a) Two API calls per item: `findNearestAddress` may be followed by `postalCodeLookup`, both counting against the limit. Simplest: once dispatched and past the gate, let the item make both (at most one call over budget), matching Node; alternative is to re-check between calls. (b) UI surfacing: the two internal queues are a geo detail; decide whether "waiting on rate budget" must appear as a distinct sub-state in the Indexer UI, or whether it is enough that the geo stage shows "blocked by rate" via its internal API queue's block reason. (c) Counter reset: port the hour/day rollover reset; the kick timer must align with those resets (just after the boundary, small buffer, like Node's +30s). (d) Where the geo-api queue lives: created and owned inside geo (geo owns the rate condition and kick timer) but participates as part of the geo-lookup stage -- decide whether geo fully encapsulates both queues behind the existing EnqueueLookup hook (pipeline unaware of the split; simpler) or exposes the API queue to the pipeline.

## Implementation order (suggested)

1. Queue: add RegisterGate/clear, replace the CanDispatch check with short-circuit gate evaluation recording the block reason, add the event stream + subscribe, add the block reason to GetStatus; remove SetCanDispatch / SetOnDrained.

2. Pipeline: register the "resource" gate per gated stage; subscribe to upstream events and kick dependents on drained (delete OnDrained); keep Apply/live re-wire working (clear + re-register gates).

3. SSE: add `GET /api/admin/pipeline/events` under the admin group, modeled on frames' events; broadcaster subscribes to queue events and pushes per-stage snapshots (queue fields + pipeline enabled/identity overlay). Auth: EventSource cannot send an Authorization header, but AuthMiddleware already falls back to validating the refreshToken cookie (used for media requests); the browser sends it automatically on same-origin requests, so an admin-route EventSource authenticates via the cookie path and AdminMiddleware reads the role it set.

4. Client: replace the setInterval poll in pl-admin-indexer.js with an EventSource feeding the existing in-place #patchCard/render; keep the manual refresh button as a one-shot fetch; bump web/sw.mjs VERSION.

5. Geo: split geo-lookup vs geo-api queues; register the "rate" gate on the API queue; add the rollover kick timer; move the API call behind the late cache re-check; remove RATE_LIMITED mark-and-skip.

## Non-goals

No server-side event throttling: events are emitted per transition and the CLIENT coalesces DOM updates (buffer messages, flush once per requestAnimationFrame) so bursts do not thrash layout; idle = no events = no work. No change to the fixed data-flow graph or per-stage concurrency semantics. No new persistence beyond the existing geo rate-limit state file.
